# デモ動画 台本（本番環境版・約3分）

提出用の録画はこの台本を使います。ローカル起動版の台本は本ファイル下部（付録）に残してあります。

- **収録対象**: https://app-mimamoritai-hack.azurewebsites.net/ （ハッカソン用。審査後は停止します）
- **想定尺**: 2分45秒〜3分（提出動画は短いほど見てもらえます）
- **音声**: ナレーションを吹き込む前提。無音で作る場合は各カットのナレーション文をテロップにしてください。

## 収録済みの動画

この台本で実際に収録した動画がリポジトリに入っています。

- **[docs/demo/mimamoritai-demo.mp4](demo/mimamoritai-demo.mp4)**（1920x1080 / 24fps / 3分11秒 / 約3.7MB・字幕焼き込み）
- 収録方法: 本番環境を Edge のアプリモード（`--app=<URL>` ＋専用プロファイル）で開き、`ffmpeg -f gdigrab` で画面録画。操作は Windows Computer Use MCP から実行
- **審査後に Azure リソースを停止しても、この動画だけは残ります**

## この動画で伝えること（順番を守る）

1. **本人が楽になる** … 足が不自由でも、リモコンの場所まで歩かずに「エアコンつけて」で操作できる
2. **でも危険な操作はさせない** … 火を使う家電は、AIがどう判断しても最終段のルールが止める
3. **その操作が、そのまま家族の安心になる** … 家族はカメラなしで「いつもどおり動けている」を知る

「安全な設計です」から入らないこと。**まず本人が助かる話**をして、そのあとで「だから任せる範囲を絞った」と続けます。

## 収録前チェック

- [ ] ブラウザをアプリモード（`--app=<URL>`）＋専用プロファイルで開く（タブ・ブックマーク・個人情報が映らない）
- [ ] 画面倍率 100%、キャプチャ領域は 1920x1080
- [ ] 事前に一度ページを開いて 3Dモデルをキャッシュさせておく（初回は読み込みに約2秒かかる）
- [ ] **家電4台をすべて「停止中」に戻しておく**（前回の収録で扇風機が点いたままだと導入が成立しない）
- [ ] 通知・チャットアプリを終了（ポップアップ映り込み防止）
- [ ] 録画は 1080p / 24〜30fps

## タイムライン

### 0:00–0:20 オープニング（トップ画面）

**映像**: トップページ。3Dマスコットが動いている状態と「お母さんの今日」カードを数秒見せる。

**ナレーション**:
> 離れて暮らす高齢の家族を、カメラを使わずに見守るサービス「見守り隊」です。
> 見守られる本人にとっても、見守る家族にとっても、負担が減ることを狙って作りました。

**ポイント**: 最初の5秒でマスコットが動いていること。止まって見えると印象が悪いので、読み込み完了を待ってから録画開始。

---

### 0:20–1:00 本人側：移動しないで家電を操作できる

**映像1**: 「家電の状態」を開き、4台すべてが**停止中**であることを見せてから閉じる。

**ナレーション**:
> 足腰が弱ってくると、リモコンを取りに行くこと自体が一仕事になります。
> このサービスでは、移動しないで、ふつうの言葉で話しかけるだけで操作できます。

**映像2**: チャット欄に「**暑いから扇風機つけて**」と入力して送信 → 「扇風機 をつけます。よろしいですか？」が返る → 「**はい**」と答えて実行。

**ナレーション**:
> 「暑いから扇風機つけて」。命令の言い方を覚える必要はありません。
> 実行の前には必ず確認を挟みます。聞き間違いで勝手に動くほうが怖いからです。

**映像3**: 「家電の状態」を開き、**扇風機だけが「使用中」に変わっている**ことを見せる。右側の「家の中の様子」にも記録が増えている。

**ポイント**: マイクボタンも一瞬見せる（音声入力できることの提示）。ただし録音はしない。

---

### 1:00–1:45 ★でも、危ない家電はAIに任せない

ここに最も尺を割きます。**審査で効くのはここです。**

**映像1**: チャット欄に「**寒いからストーブつけて**」と入力して送信。

**ナレーション**:
> 一方で、任せない範囲もはっきり決めています。
> ここがこのプロジェクトでいちばん時間をかけた部分です。

**映像2**: 「電気ストーブ は安全のため音声・チャットからの操作を禁止しています。」と返り、**確認すら出ない**こと、**機器カードが停止中のまま変化しない**ことを見せる（カードをカーソルで指す）。

**ナレーション**:
> ヒーター類は「危険」に分類しています。
> AIがどれだけ自信を持って「ONにしろ」と判断しても、最終段のルールが必ず止めます。

**映像3**: 続けて「**じゃあストーブ消して**」と入力 → 今度は受理され、確認のうえ実行される。

**ナレーション**:
> ただし「消す」は通します。危険な機器を消すのは、安全性を高める操作だからです。
> ONは拒否、OFFは許可。この非対称さが安全設計の要です。

**映像4**（任意）: 管理画面の操作ログ（`DeviceCommand`）を開き、拒否された行が記録されていることを見せる。

**ナレーション**:
> そして拒否も含めて、すべての試行を記録します。
> AIが何をしようとしたかを後から追えなければ、安全だとは言えないからです。

---

### 1:45–2:25 家族側：カメラを付けずに様子がわかる

**映像**: 「家族との共有」を開く。LINE連携済みの状態（ID・友だち追加QR）を見せ、宛先を選んで「**今日のお母さんの様子は？**」を送信 → 共有メッセージ欄に応答が並ぶ。

**ナレーション**:
> 家族はLINEで聞くだけです。専用アプリは要りません。
> いま見たとおり、本人が楽をするための操作は、そのまま家族への便りになります。
> 「暑いから扇風機つけて」は、家族から見れば「今日も普段どおり動けている」という情報です。

**ポイント**: 応答の待ち時間は編集でカット。**個人のLINEアカウントは映さない**（アプリ内の共有パネルで見せる）。

---

### 2:25–2:45 実データが流れていること

**映像**: 「詳しい情報・デモ操作」を開き、接続状況（AI / Fabric / LINE が接続済み、モデル名）を映し、「Fabricへ送信」を押す。

**ナレーション**:
> 実際のSwitchBotデバイスから、電力データがMicrosoft Fabricに流れ込んでいます。
> LINE、SwitchBot、Fabric、LLM、すべて実連携で動作しています。

---

### 2:45–3:00 クロージング

**映像**: トップページに戻り、マスコットを映して終わる。

**ナレーション**:
> 本人は移動しなくてよくなり、家族はカメラなしで様子がわかる。
> AIは会話には使いますが、危険な判断はさせません。
> APIキーが1つも無くても、`dotnet run` だけで全機能のデモが動きます。

## 撮り直しが必要になりやすい箇所

| 症状 | 対処 |
|---|---|
| マスコットが動かない | 読み込みに約2秒かかる。表示直後に録画開始しない |
| 応答が遅い | LLM応答は数秒かかる。編集でカットする前提で撮る |
| 機器カードが勝手にONになる | 実機が別の要因で動作した可能性。撮り直す |
| 確認への「はい」を飛ばした | 確認を保留したまま次の指示を送ると、**その指示が「はい／いいえ」の返事として消費される**。1コマンド＝1確認を必ず守る |
| 開始時に家電が点いている | 「4台とも停止中」から始めないと変化が伝わらない。収録前にOFFへ戻す |

# 付録：ローカル起動版 台本（約5分）

前提: `dotnet run --project src/MimamoriTai.Web` を実行済みで、ブラウザでダッシュボード（`https://localhost:xxxx/`）を開いている状態からスタートします。秘密情報の設定は一切不要です。

> ℹ️ デモ世帯には4台の機器が登録されています。「リビング照明」「寝室照明」「扇風機」は `SafetyClass.Safe`、**「電気ストーブ」は `SafetyClass.Restricted`**（危険機器）です。この電気ストーブが、本デモの目玉である「安全ガードレールによる拒否」を実演するための機器です。

## タイムライン

### 0:00–0:30 — オープニング

- ダッシュボード上部の見出し「CareRoute AI 見守り隊」と、右上の連携ステータスチップ（Devices: Mock, OrcaRouter: Mock, Fabric: Local, LINE: Mock, DB: SQLite）を指して一言:
  > 「離れて暮らす家族向けの見守りサービスです。秘密情報が一切なくても、この画面はすべてモックで動いています。」

### 0:30–1:00 — 現在の見守りステータスを見せる

- 画面左上の「現在の見守りステータス」カードを指す。
- 「これはAIの判断ではなく、ルールベースのロジック（`RiskAssessmentService`）でスコアリングしています」と説明。

### 1:00–1:45 — 自然言語での家電操作（成功パス）

1. 「自然言語で操作・質問」カードのクイックボタン **「リビングのライトつけて」** をクリック。
2. チャットログに応答（「リビング照明をつけました。」等）が表示されるのを見せる。
3. 「デバイス」セクションの「リビング照明」カードが `ON` に変わることを見せる。
4. 説明:
   > 「この操作は裏側でAI（OrcaRouter、今はモック）が意図を解析し、確信度が0.85以上、かつ機器が"Safe"に分類されている場合のみ実行されます。」

### 1:45–2:45 — 安全ガードレールのデモ（拒否＋監査）

1. 入力欄に **「ストーブつけて」** と入力して送信（クイックボタンには無いので手入力）。
2. 応答が **「電気ストーブ は安全のため音声・チャットからの操作を禁止しています。」** となり、デバイスカードの「電気ストーブ」が **OFFのまま変化しない**ことを見せる。
3. 説明:
   > 「電気ストーブはヒーター類なので `SafetyClass.Restricted` に分類されます。AIがどれだけ自信を持って"ONにしろ"と判断しても、ルールベースのガードレール（`DeviceSafetyPolicy`）が最終段で必ずブロックします。AIの出力は決して信用しません。」
4. 続けて **「ストーブ消して」** と入力して送信し、今度は**受理される**ことを見せる（「消します。よろしいですか？」と確認が入るので「はい」と答える）。
   > 「ただしOFFは許可します。危険機器を"消す"のは安全性を高める操作だからです。ON禁止・OFF許可という非対称な設計が、実際の安全設計の考え方です。」
5. 「そして重要なのは、この**拒否も含めてすべての試行が監査ログ（`DeviceCommand`）として記録される**という点です。成功も失敗も拒否も、後から誰が・いつ・何を試みたか追跡できます。」（DBの中身をSSMS等で見せられる場合はここで見せる）

### 2:45–3:30 — 生活データへの質問

1. クイックボタン **「今日のお母さんどう？」** または **「今日最初に活動したのは何時？」** をクリック。
2. 応答が生活データに基づいた具体的な内容であることを確認。
3. 説明:
   > 「これは Microsoft Fabric Data Agent が未設定の間、アプリ内蔵のロジック（`LocalDataQuestionService`）がデータベースから直接答えています。Fabricを設定すれば、より高度な自然言語分析にシームレスに切り替わります。」

### 3:30–4:15 — LINEシミュレーターと家族共有フィード

1. 「LINE シミュレーター」で発言者を「娘」に切り替え、**「今日の様子教えて」** と入力して「LINEで送る」をクリック。
2. 「家族共有フィード」に発言とAI応答が時系列で追加されるのを見せる。
3. 説明:
   > 「実際のLINE公式アカウントと連携すれば、家族はLINEグループの会話だけでこの全機能を使えます。」

### 4:15–4:45 — 異常パターンの検知デモ

1. （Development環境限定）「デモ用シミュレーション」から **「深夜活動異常」** ボタンをクリック。
2. ページ上部の「現在の見守りステータス」カードのリスクレベル・理由が変化することを見せる。
3. 説明:
   > 「深夜帯（0〜5時JST）の家電利用や、普段より少ない活動量などをルールベースで検知し、家族に伝えます。」

### 4:45–5:00 — クロージング

> 「AIは会話や意図理解には使いますが、危険な操作の最終判断は必ずルールベースのガードレールが行い、すべての試行を監査ログに残す設計です。秘密情報ゼロで今すぐ試せます。」
